# V.23 / V23C support

V23C is the Conexant command name for V.23. The dedicated answerer accepts:

- `--v23` or `--v23c`: 1200 bit/s server transmit, 75 bit/s server receive.
- `--v23-reverse`: 75 bit/s server transmit, 1200 bit/s server receive.

Use the option instead of `--v90` or `--v32bis` for a dedicated instance. Preserve the usual AudioSocket port and PPP settings for that instance.

## Dedicated calling route

For an isolated tone/data test, start a second daemon on the same host as Asterisk:

```sh
./sm_daemon --v23 --listen 127.0.0.1 --port 9106 --no-ppp --echo --log-dir /tmp/softmodem-v23
```

Merge the `5551023` extension and `*995551023` alias from `asterisk/extensions.conf.example` into the matching Asterisk contexts, then reload the dialplan. Dial `5551023` (or the alias) to reach this instance. These are example extensions; they become usable only after the daemon and dialplan are configured. Keep the existing high-speed route on its own port.

On a Conexant caller, select transparent V.23 with `AT%C0` and `AT+MS=V23C,0` before dialing. In this echo test, transmitted characters should return after the connection establishes. For PPP, remove `--no-ppp --echo` and supply the deployment's PPP addresses, DNS, and networking hooks. Use addresses reserved for this instance to avoid conflicts with other callers. The 75 bit/s return channel can make normal PPP and website timeouts unsuitable.

Verification on October 10, 2026: all eight targeted offline checks passed (four DSP, three C-interface, one V.8 selection). This verifies the software paths, not a physical modem connection.

The normal V.8 menu also offers V.23 duplex. If both ends select it, the answerer hands off to the 1200/75 transparent engine after V.8, clearing the LAPM state. V.34, V.32bis and V.22bis retain their higher preference. V.23 half-duplex is not advertised.

## Legacy callers on the normal number

The BinModem answerer also tries a non-V.8 compatibility sequence on the same normal route. After unanswered V.8, the existing V.32 opening-tone detection retains priority. Otherwise the answerer starts V.22bis, listening for a qualified 1200 Hz V.22 caller mark or a 1270 Hz Bell 103 caller mark. Five seconds without either response starts a three-second Bell 103 2225 Hz mark probe; no response then starts the V.23 1300 Hz forward mark. The V.23 engine waits for the caller's 75-baud back channel before reporting connection. Silence alone never produces CONNECT.

The probe durations are implementation policy, not a standardized V.8 ladder. Detection uses 40 ms windows and 200 ms qualification. The similar 2225/2250 Hz answering tones are not accepted as caller responses. A qualified V.22 caller stays with the V.22bis engine; V.8-negotiated V.22bis bypasses probing. Bell 103 carries transparent 300/300 asynchronous 8N1 data without V.42/V.42bis.

On October 11, 2026, one Conexant USB modem call per mode through Callcentric reached CONNECT on the normal route for Bell 103 (300/300) and legacy V.23 (1200 down/75 up). Neither completed PPP: Bell 103 did not obtain an IP address within the bounded readiness test, and V.23 ended with an LCP timeout. These trials verify hardware startup, not reliable PPP or sustained data delivery. Reverse-mode hardware interoperability remains unverified.

The mode carries transparent asynchronous 8N1 bytes. It does not negotiate V.42/V.42bis. Configure the calling modem for a matching transparent V.23 connection; the Conexant carrier name is `V23C`. A 75 bit/s direction is extremely slow for PPP negotiation and IP packets.

Implementation uses the ITU-T V.23 (11/1988) tone assignments: 1300/2100 Hz for 1200 baud, 1300/1700 Hz for 600 baud, and 390/450 Hz for the optional 75-baud return channel. The 600-baud primitives exist, but the daemon options select the 1200/75 pair.

Validation: tone/direction checks; byte recovery with noise, independent clocks at +/-500 ppm and 8/16 kHz; two-way streaming and carrier loss; actual 8 kHz C-interface connection status and complementary rate reporting. V.8-to-V.23 tests exchange bytes in both directions through both the linear and resampled C-interface paths, and verify that LAPM is disabled. Hardware interoperability still requires verification.
